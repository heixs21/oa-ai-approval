# 泛微 E9 AI 自动审批技术方案

> 版本 v0.1 ｜ 2026-11-18
> 范围：专用账号 + 开放接口 + 下载 servlet + 大模型评审，全流程自动化

---

## 1. 目标与边界

**目标**
专用账号登录泛微 E9，轮询待办，拉取流程表单与附件，交由大模型按规则生成评审意见，自动回填并提交，全程留痕可审计。

**边界（重要）**
- 不修改泛微任何代码，不装插件，不动数据库结构
- 只使用三类入口：开放接口 `/api/...`、登录接口 `/api/hrm/login/checkLogin`、下载 servlet `/weaver/weaver.file.FileDownload`
- 所有状态、日志、审计数据落在本系统自己的库里

**前提**
- 专用账号已建好，且对目标流程有审批权限
- 开放接口 appid / secret 已申请
- 账号未启用图形验证码或双因子（否则登录接口会失败）

---

## 2. 整体链路

```
①取token → ②拉待办 → ③读详情 → ④提fileid → ⑤登录+下载 → ⑥落盘 → ⑦AI评审 → ⑧提交
```

| # | 步骤 | 接口 / 动作 | 鉴权方式 |
|---|---|---|---|
| ① | 获取 token | `POST /api/ec/dev/auth/applytoken` | appid + cpk |
| ② | 拉待办列表 | `POST /api/workflow/paService/getDoingWorkflowRequestList` | token |
| ③ | 读流程详情 | `POST /api/workflow/paService/getWorkflowRequest` | token |
| ④ | 提取 fileid | 正则解析 `fieldShowValue` | — |
| ⑤ | 登录拿会话 | `POST /api/hrm/login/checkLogin` | loginid + userpassword |
| ⑥ | 下载附件 | `GET /weaver/weaver.file.FileDownload?fileid=&download=1` | JSESSIONID |
| ⑦ | 落盘 | 本地按流程建目录 | — |
| ⑧ | AI 评审 | 大模型（表单 + 附件 + 历史意见） | — |
| ⑨ | 提交流程 | `POST /api/workflow/paService/submitRequest` | token |

**已实测的请求方法**（泛微这套接口方法不统一，别假设都是 POST）：

| 接口 | 方法 | 鉴权 | 备注 |
|---|---|---|---|
| `getDoingWorkflowRequestList` | POST | appid+token+userid | 已验证 |
| `getWorkflowRequest` | **GET** | appid+token+userid | 实测 POST 返回 405 |
| `FileDownload` | **GET** | JSESSIONID | 独立路径，不走 token |
| `checkLogin` | **POST** | 无（换取 session） | 参数走 query string |
| `submitRequest` | POST | appid+token+userid | 参数走 query string |

代码里用 `METHOD_MAP` 记录已知方法，撞到 405 时自动换另一种并记住。

## 3. 关键结论：两个 id 千万别混

这是整个方案最容易出错的地方，先钉死。

以你给的真实返回为例，附件字段 `fjsc`：

| 位置 | 值 | 含义 |
|---|---|---|
| `fieldValue` | `32352,32353` | **docid**（文档库主键） |
| `fieldShowValue` 里的 `fileid` | `35991,35992` | **imagefileid**（下载接口要的） |
| `fieldShowValue` 里的 `filename` | `1.jpg,2.jpg` | 原始文件名 |

下载接口 `/weaver/weaver.file.FileDownload?fileid=` 要的是 **imagefileid**，也就是 HTML 里那个。

**结论：直接用 `fieldShowValue` 正则提取，不要碰 `fieldValue`。**

这样做的两个好处：
1. 一次就拿到 `fileid` + `filename`，不用再查 `docdetail` / `imagefile` 表；
2. 文件名是原始的，不用自己做 docid→文件名的映射。

### 提取代码

```python
import html, re, urllib.parse

FILE_PATTERN = re.compile(r"fileid=(\d+)[^'\"]*?(?:filename=([^'\"&)]+))?")

def extract_files(field_html: str):
    """从附件字段的 HTML 里提取 [(imagefileid, filename), ...]"""
    if not field_html:
        return []
    text = html.unescape(field_html)          # 处理 &amp; 转义
    result = []
    for m in FILE_PATTERN.finditer(text):
        fid = m.group(1)
        name = urllib.parse.unquote(m.group(2) or f"file_{fid}")
        result.append((fid, name))
    return result
```

### 三个必须处理的边界

1. **多个附件字段**：一个表单可能有 `fjsc`、`fjsc2`……判断依据是 `fieldHtmlType == "6"`，要遍历**所有**这类字段，不能只认 `fjsc`。
2. **`&amp;` 转义**：HTML 里常写成 `fileid=35991&amp;filename=1.jpg`，不 unescape 就匹配不到 filename。
3. **字段为空**：`fieldShowValue` 为空字符串或 `<br/><br/>`，要判空跳过，不要当成"有附件"。

## 4. 鉴权：两套凭据，两套生命周期

**这是本方案最容易被低估的部分。** token 和 JSESSIONID 完全独立，不能互相替代。

| 凭据 | 服务对象 | 获取方式 | 典型有效期 | 失效表现 |
|---|---|---|---|---|
| `token` | `/api/` 开放接口 | `applytoken` | 约 30 分钟 | 返回业务错误码（如 token 过期/无效） |
| `JSESSIONID` | `/weaver/` 老 servlet | `checkLogin` | 约 30 分钟（Tomcat session-timeout） | **HTTP 200 + 一个登录页 HTML** |

### 业务接口的请求头

| 请求头 | 必填 | 说明 |
|---|---|---|
| `appid` | 是 | 许可证号码 |
| `token` | 是 | `applytoken` 拿到的令牌 |
| `userid` | 是 | **不是明文**，是用 `spk` 公钥 RSA 加密后的密文 |
| `skipsession` | 否 | 是否跳过 session 拦截（白名单接口用），1=是，0=否（缺省） |
| `Content-Type` | 否 | 实测用 `application/json`。文档写的 form-urlencoded 配 JSON body 会返回空响应 |

**三个容易踩的点：**

**1. `userid` 必须加密。** 用注册许可 `/api/ec/dev/auth/regist` 返回的 `spk` 公钥，对 userid 做 RSA（PKCS1 v1.5）加密再 base64：

```python
pem = "-----BEGIN PUBLIC KEY-----\n" + spk + "\n-----END PUBLIC KEY-----"
pub = serialization.load_pem_public_key(pem.encode())
cipher = pub.encrypt(str(userid).encode(), padding.PKCS1v15())
userid_header = base64.b64encode(cipher).decode()
```

注意 `spk` 是裸的 base64 串，要自己补上 `BEGIN/END` 头尾才能被解析。

**2. `Content-Type` 必须和 body 形态匹配（实测结论，和文档有出入）。**

文档写的是「POST 必须设 form-urlencoded」，但实测下来，**JSON body 配 form-urlencoded 会返回空响应**，`r.json()` 直接报 `Expecting value: line 1 column 1 (char 0)`。实测可用的组合只有两种：

| body 形态 | Content-Type | 结果 |
|---|---|---|
| JSON 字符串 | `application/json` | ✅ 正常 |
| 表单参数 | `application/x-www-form-urlencoded; charset=utf-8` | ✅ 正常 |
| JSON 字符串 | `application/x-www-form-urlencoded; charset=utf-8` | ❌ 空响应 |

本项目默认走第一种。用 requests 时要注意：如果用 `json=payload`，requests 会自动把 Content-Type 设成 `application/json`；如果要自己控制，就用 `data=json.dumps(...)` 并显式给头。

另外，接口**响应**的 Content-Type 是 `text/plain; charset=utf-8`，但内容本身是 JSON 数组，`r.json()` 能正常解析，不要被这个头误导。

GET 请求（如 `checkLogin`）不需要设 Content-Type。

**3. userid 填哪个值。** 就是专用账号的用户主键。以「接口账号」为例，从流程日志的 `operatorId` 字段能直接看到（示例数据里是 `369`）。

### token 管理策略

- 内存缓存，**提前 5 分钟主动刷新**，不要等过期
- 收到"token 失效"类错误码时，强制刷新并**重试一次**
- 单例 + 互斥锁，避免多线程同时刷新把旧 token 顶掉

### checkLogin 的四个坑

1. **返回 200 不等于登录成功**，必须校验响应里 `Set-Cookie` 是否含 `JSESSIONID`；
2. **参数用 form 提交**：`loginid`、`userpassword`，字段名以实际抓包为准；
3. **负载均衡无 session 粘滞时**，JSESSIONID 可能只在某一台应用服务器有效，下载会偶发失败——遇到"间歇性下载失败"优先怀疑这个；
4. **账号开验证码/双因子**会直接失败，必须给专用账号单独关掉。

### 下载成功的判定（关键）

不能只看 HTTP 状态码。会话失效时它返回的是 **200 + `text/html`**：

```python
r = sess.get(url, params={"fileid": fid, "download": 1},
             stream=True, timeout=(10, 60))

ct = r.headers.get("Content-Type", "")
cd = r.headers.get("Content-Disposition", "")
if "text/html" in ct or not cd:
    # 会话已失效，标记后重新登录再重试
    raise SessionExpired()
```

## 5. 分步详解

### 5.1 获取 token

```
POST /api/ec/dev/auth/applytoken
Headers: appid, secret
```

- 直接用 `appid` + `secret` 两个请求头，不需要自己算 cpk
- 返回体里取 `token`
- 缓存起来，后续所有 `/api/` 请求带 `appid` + `token` + `userid` 三个头

### 5.2 拉待办列表

```
POST /api/workflow/paService/getDoingWorkflowRequestList
Headers: appid, token, userid
Body: { pageNo, pageSize, ... }
```

**要点**
- 只拉第 1 页 + 按时间倒序即可，不必全量翻页
- 关注返回里的 `requestId`、`requestName`、`workflowId`、`currentNodeId`、`currentNodeName`
- **用本地已处理表做去重**，不要依赖接口返回的顺序

### 5.3 读流程详情

```
POST /api/workflow/paService/getWorkflowRequest
Headers: appid, token, userid
Body: { requestId, workflowId }
```

**前置校验（拿到就判，省事）**
- `canView == false` → 账号无权限，跳过并记录
- `currentNodeName` 不在白名单节点 → 跳过（不是所有节点都该自动批）

**可用的上下文**（除表单外都别浪费）
- `workflowMainTableInfo.requestRecords[0].workflowRequestTableFields`：表单字段
- `workflowRequestLogs`：历史审批记录，**含前面每个人的意见**
- `mustInputRemark`：为 `true` 时 remark 必填

### 5.4 提取 fileid

按第 3 节的规则，遍历所有 `fieldHtmlType == "6"` 的字段。

### 5.5 登录 + 下载

```python
# 1. 登录
s = requests.Session()
r = s.post(f"{OA}/api/hrm/login/checkLogin",
           data={"loginid": USER, "userpassword": PWD}, timeout=10)
if not s.cookies.get("JSESSIONID"):
    raise LoginFailed(r.text[:300])

# 2. 下载（逐个 fileid）
for fid, fname in files:
    resp = s.get(f"{OA}/weaver/weaver.file.FileDownload",
                 params={"fileid": fid, "download": 1},
                 stream=True, timeout=(10, 120))
    ...
```

- **流式写盘**，不要 `resp.content` 一次性读进内存
- 下载完比对 `Content-Length` 与实际字节数
- 单文件失败不影响其它文件，逐个记录结果

### 5.6 落盘

目录规范：

```
{STORAGE_ROOT}/{requestId}_{清洗后的流程名}/
    ├── meta.json          # 流程快照、字段、历史意见
    ├── 1.jpg
    └── 2.jpg
```

- 流程名要清洗 Windows 非法字符 `\ / : * ? " < > |`，并限制长度（建议 60 字符）
- 同名文件加序号后缀，不要覆盖
- `meta.json` 存一份原始返回，出问题时可复现

### 5.7 AI 评审

**输入构造**

```
【流程信息】
流程名称：工作联系单
当前节点：03 - 接单人确认
申请人：张三（内销处）
申请日期：2025-02-05

【表单内容】
流程编号：GZLXD-20250205-00063
相关说明：销售员电脑于2020年9月20日购买……需要更换新电脑，请领导核实批准。
公司名称：示例机电股份有限公司

【历史审批】
- 王五（高层管理）2025-02-05 批准，意见：无
- 李四（IT）2025-02-05 批准，意见：无

【附件】
1.jpg（190K，图片）
2.jpg（81K，图片）
```

**审核要点（合同评审）**

1. **形式与要素**：合同主体名称、签署方、日期、签章是否完整一致，与申请内容是否吻合
2. **重大错误**：金额数字（小写与大写是否一致）、计量单位是否正确，有无明显笔误或前后矛盾
3. **重大风险条款**：其他合同当事人的主体资格是否适格、是否存在履约能力的重大瑕疵；有无对我司明显不利、责任严重失衡的条款
4. **条款合理性**：产品名称、技术参数、规格、型号、配置、重量等是否清晰准确；质量要求、交货期、质保期、包装、检验方式；合同价款及其支付方式、条件、期限；违约责任是否明确、合理
5. **材料完整性**：附件是否齐全、能否辨认，与申请说明是否一致

**输出必须结构化**，不要让它自由发挥：

```json
{
  "decision": "approve | manual",
  "confidence": 0.0,
  "remark": "写入流程的意见，分点论述，≤500 字",
  "evidence": ["判断依据要点"]
}
```

注意 `decision` 只有两个值——AI 只批不退，拿不准一律走 `manual`。

**四条硬规则**
1. `confidence < 阈值` → 强制 `manual`，转人工
2. 附件解析失败（图片模糊、PDF 加密、格式不支持）→ 强制 `manual`，**不许瞎猜**
3. `remark` 必须是能给人看的话，有依据、不空洞；禁止出现"AI 认为"这类表述
4. `remark` 分点撰写，控制在 500 字以内（原 200 字上限已放开）

**附件处理：交给 DeepSeek 服务端解析**

用 `deepseek-flash`（DeepSeek-V4.1-Flash）的文件输入能力，**本地不需要 OCR，也不需要 pypdf / python-docx**：

```python
# 1. 上传附件
with open("1.jpg", "rb") as f:
    up = client.files.create(file=f, purpose="text_recognition")

# 2. 在 messages 里引用（注意是平铺的 file_id）
messages = [{
    "role": "user",
    "content": [
        {"type": "text", "text": material},
        {"type": "file", "file_id": up.id},
    ],
}]
```

**引用方式是平铺的 `file_id`，不是 OpenAI 那种嵌套 `file` 对象。** 实测三种写法：

| 写法 | 结果 |
|---|---|
| `{"type":"file","file_id": id}` | ✅ 成功 |
| `{"type":"file","file":{"file_id": id}}` | ❌ `file must have a file_id or file_data` |
| `{"type":"file","file":{"file_data": b64}}` | ❌ 同上 |

**`purpose` 只能填这三个**（实测）：

```
text_recognition  /  rich_layout_recognition  /  user_data
```

推荐 `text_recognition`，PDF 和图片都能识别；`user_data` 传 1.5MB 以上的文件容易连接中断。网上流传的 `assistants`、`file-extract` 都不支持——前者返回 `550`，后者返回 `400`。

支持 **PDF / Word / PPT / 图片**，服务端自动解析，图文混排的 PDF 也能识别图里的内容。所以：

| 类型 | 处理 |
|---|---|
| 图片 jpg/png | 直接上传，服务端识别 |
| PDF（含扫描件） | 直接上传，服务端解析 |
| Word / PPT | 直接上传 |
| Excel | 建议转成 PDF 或截图再传 |

注意两点：`base_url` 要用 `https://api.deepseek.com/v1`；上传的文件记得用完删掉，否则服务端会堆积。

### 5.8 提交流程（已确认）

```
POST /api/workflow/paService/submitRequest?requestId=60110&remark=<URL编码后的意见>
Headers: appid, token, userid
```

- 参数走 query string：`requestId`、`remark`
- `remark` **必须 URL 编码**，中文、换行、标点都要处理
- AI **只批不退**，不需要传审批动作参数
- 返回 `{"code":"SUCCESS"}` 视为成功

**提交前二次校验**
- 重新拉一次待办，确认 requestId 仍在待办里（防止人工已处理）
- 提交后校验返回码，成功才写状态

**返回失败时**：不要盲目重试。先判断是"已经被处理"（视为幂等成功）还是真失败，两者处理方式完全不同。

## 6. 本地状态表

```sql
CREATE TABLE t_ai_approval (
  id            BIGINT PRIMARY KEY AUTO_INCREMENT,
  request_id    VARCHAR(32)  NOT NULL,
  workflow_id   VARCHAR(32),
  node_id       VARCHAR(32)  NOT NULL,      -- 去重关键
  request_name  VARCHAR(500),
  status        VARCHAR(20),                -- 见状态机
  decision      VARCHAR(20),
  confidence    DECIMAL(4,3),
  remark        TEXT,
  attach_count  INT DEFAULT 0,
  retry_count   INT DEFAULT 0,
  err_msg       VARCHAR(1000),
  create_time   DATETIME,
  update_time   DATETIME,
  UNIQUE KEY uk_req_node (request_id, node_id)
);
```

**去重键用 `(request_id, node_id)`，不是只用 `request_id`。**

原因：同一个流程会被退回重提，会重新回到同一节点；只用 request_id 会导致第二轮不再处理。用 node_id 又会漏掉"退回后再次回到同一节点"——所以完整方案是 `(request_id, node_id, 待办生成时间)`，或者更简单：**提交成功后把该 request 从待办里消失作为成功标志，失败重试有上限**。

## 7. 状态机

```
DISCOVERED → FETCHED → ATTACH_OK → AI_REVIEWED → SUBMITTED
     ↓           ↓          ↓            ↓
   SKIPPED     FAILED    MANUAL       MANUAL
```

| 状态 | 含义 | 后续动作 |
|---|---|---|
| `DISCOVERED` | 待办命中 | 拉详情 |
| `SKIPPED` | 不在白名单 / 无权限 | 结束 |
| `FETCHED` | 详情已取 | 处理附件 |
| `ATTACH_OK` | 附件已落盘 | 送 AI |
| `AI_REVIEWED` | 意见已生成 | 提交 |
| `SUBMITTED` | 提交成功 | 结束 |
| `MANUAL` | 转人工 | 告警，不再自动处理 |
| `FAILED` | 异常 | 重试，超过 3 次转 MANUAL |

---

## 8. 异常与重试

| 异常 | 处理 |
|---|---|
| token 过期 | 刷新后重试 1 次 |
| JSESSIONID 失效 | 重登后重试 1 次 |
| 附件下载失败 | 单文件重试 2 次，仍失败则整个流程转 MANUAL |
| AI 调用超时 | 重试 2 次（指数退避），仍失败转 MANUAL |
| AI 返回非法 JSON | 修复性重试 1 次，仍失败转 MANUAL |
| 提交失败 | 重试 2 次；仍失败必须告警，**不允许静默丢弃** |

**原则：宁可转人工，不可错批。** 所有失败都必须落到 `MANUAL` 并触发告警，不能悄悄跳过。

## 9. 安全与风控（重点，建议先读这一节）

自动审批是**代替人做决定**，出错的代价远大于同步附件。上线前必须做到：

1. **流程白名单**：只允许配置过的 `workflowId` + 节点自动处理，其余一律跳过
2. **金额/类型阈值**：涉及金额、人事、合同类的，超过阈值强制转人工
3. **置信度门限**：`confidence` 低于阈值不提交
4. **两阶段上线**
   - 阶段一 **建议模式（dry-run）**：只生成意见写日志，**不提交**。跑 2~4 周，人工比对准确率
   - 阶段二 准确率达标后，才开自动提交
5. **退回次数熔断（必须做）**：同一流程被人工退回 2 次以上，立即停止自动处理、转人工。否则会形成「AI 批 → 人退 → AI 又批」的死循环，人会被反复骚扰，AI 沦为噪音源
6. **全量审计**：每条决策都要能追溯——谁、什么流程、什么表单内容、什么附件、AI 说了什么、最终提交了什么
7. **兜底开关**：一个配置项能立刻停掉全部自动提交
8. **意见措辞**：写"经核对，申请内容与附件一致，同意"，不要写"AI 判断通过"
